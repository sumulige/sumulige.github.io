# 重复提交、同源记录与同一次骑行，需要分别识别

上传一次活动后没有收到响应，再提交一次，系统是否会多建一条记录？同一次骑行分别从码表平台和另一个平台导入，是否应该合并？活动经过裁剪后再次同步，又是新活动还是原记录的新版本？这些问题都涉及重复，但判断对象不同。

原答要求幂等键中的duration_sec必须使用经过时间。经过时间通常比平台重算的移动时间少一层移动判据，但仅凭这一点还不能选定一个适用于所有问题的键。

## 1. 请求幂等首先描述操作效果

RFC9110将幂等定义在请求的预期效果上：重复相同请求，与执行一次具有相同的预期服务端效果。它并不要求每次响应逐字一致，也不排除服务端为每次请求单独保留日志。[RFC9110 §9.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)

以Stripe当前文档中的API v1为具体例子，服务端可保存某个幂等键对应的结果，检查重试参数是否一致，并在其规定条件下处理重复请求。该机制还有保留期限与执行条件；文档也明确区分v1和v2行为。它说明幂等依赖服务端合同，不能把某个服务的规则当成所有系统的永久保证。[Stripe文档](https://docs.stripe.com/api/idempotent_requests)

识别一次重试，并不要求从骑行时长推断两份文件是否来自同一场活动。相反，即使系统能让一次提交重试不新增记录，也可能仍把另一来源的同场骑行收成一条独立来源记录。

## 2. 同一事件可以有多个来源记录和修订版本

以下五份表示完全虚构，已知都属于同一场骑行。时间以某个共同起点为0秒，示例没有调用任何平台：

|表示|来源及记录ID|版本|开始秒|经过秒|移动秒|
|---|---|---:|---:|---:|---:|
|a|A / 101|1|0|3600|3180|
|a的重试|A / 101|1|0|3600|3180|
|b|B / 22|1|0|3600|3170|
|b的裁剪版|B / 22|2|60|3480|3060|
|c|C / 5|1|2|3598|3178|

比较来源、开始、经过时间三个字段，会得到4组不同值；只比较开始和经过时间，会得到3组；比较开始和移动时间，会得到4组；比较来源和记录ID，会得到3组。[全部输入与计算E2](#/article/series-guide?section=publication)

这些数量回答的是不同问题。a与重试是同一个提交内容的重复；b与裁剪版在本例约定下是同一来源记录的不同版本；A、B、C则保留了三种来源身份。它们都属于一场骑行这一信息来自构造前提，并非某种字段组合已经成功识别了真实事件。

本例没有评选生产主键。它只显示：把source加入比较，可以保留不同来源；若目标是直接将所有来源的同场骑行视为同一对象，这个字段也会使相等比较分开。开始时间和elapsed保持一致时能对齐部分表示，却仍会被裁剪和开录差异打断。

## 3. 确定性计算不能补出缺失的身份含义

对一组字段进行确定性编码，只能稳定处理已经提供的输入。它不能自行知道b是a的另一路导入，也不能知道b的裁剪版应视为原记录修订还是独立事件。这些关系来自接口合同、来源标识、版本或其他证据。

因此，把字段送进Hash并不能解决输入所指对象不明确的问题。本次直接比较字段元组，没有执行任何摘要计算，也没有实现新的键、去重表或合并策略。

时间接近可以成为关联线索，但接近本身不是身份保证。若进一步引入容差、轨迹或设备信息，仍需确定要减少哪类错误，并用真实对应关系验证；当前材料不支持给出一个统一秒数阈值。

## 4. 回到duration_sec：先看合同，再看它承担的作用

如果字段已经被定义为经过时间，它应与记录边界及版本一致地解释；如果定义为计时器时间，自动暂停就影响它所累计的部分；如果定义为移动时间，还需知道平台的计算条件。不能为方便去重而悄悄改变原字段含义。

接着需要确定系统正在识别的是一次请求、某个来源的一条记录，还是跨来源的物理骑行。只有在目标与接口保证明确后，才能判断时长是否应参与识别，以及修订怎样关联。

目前已验证的是时间定义、所读官方合同的范围，以及三组有限反例。真实系统的duration_sec合同、来源ID生命周期、跨源对应和错误表现仍缺证据，所以完整问题保持未完成应用验证。文章给出的是原答方案成立前必须弄清的关系，尚未采用任何生产身份规则。
